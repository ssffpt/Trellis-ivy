# 代码质量检查

针对最近编写的代码进行全面质量验证。结合规范合规性、跨层安全性与提交前检查。

---

## 步骤 1：识别变更内容

```bash
git diff --name-only HEAD
git status
```

## 步骤 2：读取任务产物与适用规范

读取 `task.json` 的 `check_depth` 字段（**不存在时默认 `"full"`**）。按顺序读取当前任务产物：

- `prd.md`
- `design.md`（如存在）
- `implement.md`（如存在）

```bash
python3 ./.trellis/scripts/get_context.py --mode packages
```

针对每个发生变更的包/层，阅读规范索引并遵循其**质量检查**章节：

```bash
cat .trellis/spec/<package>/<layer>/index.md
```

阅读所引用的具体指南文件——索引只是指针，而非目标本身。

## 步骤 3：运行项目检查

运行项目的 lint、类型检查和测试命令。在继续之前修复所有失败项。

> lint/test 是机械化的客观检查，不混入审核维度。

## 步骤 4：逐维度审核

根据 `check_depth` 决定执行范围：

- `"light"`：仅审核维度 1（功能正确性）和维度 6（规范合规）
- `"full"`：审核全部 6 个维度

### 1. 功能正确性

- [ ] 每个 PRD 验收标准是否都有对应的实现？
- [ ] implement.md 中的 checklist 是否逐项完成？
- [ ] 新增/修改的行为是否符合 design.md 的契约？
- [ ] 边界条件和异常路径是否处理？

### 2. 回归安全

- [ ] 修改的函数/方法的所有调用方是否已验证？
- [ ] 现有测试是否全部通过（不只是新增测试）？
- [ ] 改动的接口签名是否影响了下游消费者？
- [ ] 共享工具/常量的修改是否同步到所有使用方？

### 3. 安全基线

- [ ] 用户输入是否在系统边界处做了验证/消毒？
- [ ] 是否存在注入风险（SQL/命令/XSS/路径遍历）？
- [ ] 敏感数据是否正确处理（未泄露到日志/错误信息）？
- [ ] 新增的 API 端点是否有适当的权限控制？

### 4. 跨层一致性

- [ ] 类型/schema 变更是否跨层传播（Storage → Service → API → UI）？
- [ ] 错误是否正确传播到调用方（不吞异常、不丢上下文）？
- [ ] 数据流方向是否正确（读：Storage→UI，写：UI→Storage）？
- [ ] 创建新代码前是否搜索了现有类似代码（避免重复定义）？
- [ ] 批量修改后所有出现位置是否已同步更新？
- [ ] 导入路径是否正确（相对 vs 绝对）？无循环依赖？

### 5. 性能影响

- [ ] 新增的数据库查询是否有 N+1 风险？
- [ ] 循环内是否有重复计算或重复 IO？
- [ ] 大集合操作是否考虑了分页/流式处理？

### 6. 规范合规

- [ ] 是否遵循 `.trellis/spec/` 中的编码指南？
- [ ] 命名、目录结构、导入路径是否一致？
- [ ] 是否有残留的 debug 代码、注释掉的代码、TODO？
- [ ] `.trellis/spec/` 是否需要更新（新模式、约定、经验教训）？

> "如果我修复了一个 bug 或发现了某些非显而易见的事情，是否应该记录下来，以免将来的自己遇到同样的问题？" → 如果是，更新相关规范文档。

---

## 步骤 5：报告并修复

报告发现的违规项并直接修复。修复后重新运行项目检查。
