# 代码质量检查

针对最近编写的代码进行全面质量验证。结合规范合规性、跨层安全性与提交前检查。

---

## 步骤 1：识别变更内容

```bash
git diff --name-only HEAD
git status
```

## 步骤 2：读取任务产物与适用规范

按顺序读取当前任务产物：

- `prd.md`
- `design.md`（如存在）
- `implement.md`（如存在）

```bash
python3 ./.trellis/scripts/get_context.py --mode packages
```

针对每个发生变更的包/层，阅读规范索引并遵循其**质量检查**章节：

```bash
cat .trellis/spec/<package>/<layer>/index.md
```

阅读所引用的具体指南文件——索引只是指针，而非目标本身。

## 步骤 3：运行项目检查

运行项目的 lint、类型检查和测试命令。在继续之前修复所有失败项。

## 步骤 4：对照检查清单审查

### 代码质量

- [ ] Linter 通过？
- [ ] 类型检查通过（如适用）？
- [ ] 测试通过？
- [ ] 没有遗留的调试日志？
- [ ] 没有抑制的警告或类型安全绕过？

### 测试覆盖

- [ ] 新增函数 → 是否添加了单元测试？
- [ ] Bug 修复 → 是否添加了回归测试？
- [ ] 行为变更 → 是否更新了现有测试？

### 规范同步

- [ ] `.trellis/spec/` 是否需要更新？（新模式、约定、经验教训）

> "如果我修复了一个 bug 或发现了某些非显而易见的事情，是否应该记录下来，以免将来的自己遇到同样的问题？" → 如果是，更新相关规范文档。

## 步骤 5：跨层维度（如适用）

如果变更仅限于单层，跳过此步骤。

### A. 数据流（变更触及 3 层以上）

- [ ] 读取流追踪正确：存储 → 服务 → API → UI
- [ ] 写入流追踪正确：UI → API → 服务 → 存储
- [ ] 类型/模式在各层之间正确传递？
- [ ] 错误是否正确传播给调用方？

### B. 代码复用（修改常量、创建工具函数）

- [ ] 创建新代码前搜索了现有类似代码？
  ```bash
  grep -r "pattern" src/
  ```
- [ ] 如果 2 处以上定义了相同值 → 提取到共享常量？
- [ ] 批量修改后，所有出现位置都已更新？

### C. 导入/依赖（创建新文件）

- [ ] 导入路径正确（相对路径 vs 绝对路径）？
- [ ] 没有循环依赖？

### D. 同层一致性

- [ ] 其他使用相同概念的地方是否一致？

---

## 步骤 6：报告并修复

报告发现的违规项并直接修复。修复后重新运行项目检查。
