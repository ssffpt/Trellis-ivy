# 更新代码规范 - 捕获可执行契约

当你学到有价值的东西时（来自调试、实现或讨论），使用此技能更新相关的代码规范文档。

**时机**：完成任务后、修复 bug 后，或发现新模式时

---

## 代码规范优先规则（关键）

在本项目中，实现工作的"规范"指的是**代码规范**：
- 可执行契约（而非仅原则性文本）
- 具体签名、载荷字段、环境变量键与边界行为
- 可测试的验证/错误行为

如果变更涉及基础设施或跨层契约，代码规范的深度是强制性的。

### 强制触发条件

当变更包含以下任一内容时，应用代码规范深度：
- 新增/变更的命令或 API 签名
- 跨层请求/响应契约变更
- 数据库模式/迁移变更
- 基础设施集成（存储、队列、缓存、密钥、环境接线）

### 强制输出（7 个章节）

对于触发的任务，包含以下所有章节：
1. 范围 / 触发条件
2. 签名（命令/API/数据库）
3. 契约（请求/响应/环境）
4. 验证与错误矩阵
5. 好/基准/坏案例
6. 所需测试（含断言点）
7. 错误 vs 正确（至少一对）

## 何时更新代码规范

| 触发条件 | 示例 | 目标规范 |
|---------|------|---------|
| **实现了功能** | 添加了新的集成或模块 | 相关规范文件 |
| **做出了设计决策** | 选择可扩展性模式而非简单模式 | 相关规范 + "设计决策"章节 |
| **修复了 bug** | 发现错误处理的微妙问题 | 相关规范（如错误处理文档） |
| **发现了模式** | 找到更好的代码组织方式 | 相关规范文件 |
| **遇到了陷阱** | 了解到 X 必须在 Y 之前完成 | 相关规范 + "常见错误"章节 |
| **确立了约定** | 团队同意命名模式 | 质量指南 |
| **新的思考触发器** | "做 Y 之前别忘了检查 X" | `guides/*.md`（作为检查清单项） |

**关键洞察**：代码规范更新不仅是为了记录问题。每个功能实现都包含设计决策和契约，未来的 AI/开发者需要安全地执行。

## 规范结构概览

```
.trellis/spec/
├── <layer>/           # 每层编码标准（如 backend/、frontend/、api/）
│   ├── index.md       # 概览与链接
│   └── *.md           # 主题特定指南
└── guides/            # 思考检查清单（不是编码规范！）
    ├── index.md       # 指南索引
    └── *.md           # 主题特定指南
```

### 关键：代码规范 vs 指南 - 了解区别

| 类型 | 位置 | 目的 | 内容风格 |
|------|------|------|---------|
| **代码规范** | `<layer>/*.md` | 告诉 AI"如何安全实现" | 签名、契约、矩阵、案例、测试点 |
| **指南** | `guides/*.md` | 帮助 AI"写之前考虑什么" | 检查清单、问题、指向规范的指针 |

**决策规则**：问自己：

- "这是**如何写**代码" → 放入规范层目录
- "这是**要考虑什么**再写" → 放入 `guides/`

**示例**：

| 学习内容 | 错误位置 | 正确位置 |
|---------|---------|---------|
| "为此任务使用 API X 而非 API Y" | ❌ `guides/`（对思考指南太具体） | ✅ 相关规范文件（具体约定） |
| "做 Y 时记得检查 X" | ❌ 规范文件（对规范太抽象） | ✅ `guides/`（思考检查清单） |

**指南应该是简短的检查清单，指向规范**，而不是重复详细规则。

## 更新流程

### 步骤 1：识别你学到了什么

回答这些问题：

1. **你学到了什么？**（具体说明）
2. **为什么重要？**（防止什么问题？）
3. **它属于哪里？**（哪个规范文件？）

### 步骤 2：分类更新类型

| 类型 | 描述 | 操作 |
|------|------|------|
| **设计决策** | 为什么选择方案 X 而非 Y | 添加到"设计决策"章节 |
| **项目约定** | 在本项目中如何做 X | 添加到相关章节并附示例 |
| **新模式** | 发现的可复用方法 | 添加到"模式"章节 |
| **禁止模式** | 导致问题的事情 | 添加到"反模式"或"不要"章节 |
| **常见错误** | 容易犯的错误 | 添加到"常见错误"章节 |
| **约定** | 商定的标准 | 添加到相关章节 |
| **陷阱** | 非明显行为 | 添加警告标注 |

### 步骤 3：阅读目标代码规范

编辑前，阅读当前代码规范以：
- 了解现有结构
- 避免重复内容
- 找到更新的正确章节

```bash
cat .trellis/spec/<category>/<file>.md
```

### 步骤 4：执行更新

遵循这些原则：

1. **具体明确**：包含具体示例，而非抽象规则
2. **解释原因**：说明防止的问题
3. **展示契约**：添加签名、载荷字段和错误行为
4. **展示代码**：为关键模式添加代码片段
5. **保持简短**：每个章节一个概念

### 步骤 5：更新索引（如需要）

如果添加了新章节或代码规范状态变更，更新分类的 `index.md`。

## 更新模板

### 基础设施/跨层工作的强制模板

```markdown
## 场景：<名称>

### 1. 范围 / 触发条件
- 触发条件：<为什么这需要代码规范深度>

### 2. 签名
- 后端命令/API/数据库签名

### 3. 契约
- 请求字段（名称、类型、约束）
- 响应字段（名称、类型、约束）
- 环境变量键（必需/可选）

### 4. 验证与错误矩阵
- <条件> -> <错误>

### 5. 好/基准/坏案例
- 好：...
- 基准：...
- 坏：...

### 6. 所需测试
- 单元/集成/E2E 及断言点

### 7. 错误 vs 正确
#### 错误
...
#### 正确
...
```

### 添加设计决策

```markdown
### 设计决策：[决策名称]

**背景**：我们在解决什么问题？

**考虑的方案**：
1. 方案 A - 简要描述
2. 方案 B - 简要描述

**决策**：我们选择方案 X，因为...

**示例**：
\`\`\`typescript
// 实现方式
code example
\`\`\`

**可扩展性**：将来如何扩展...
```

### 添加项目约定

```markdown
### 约定：[约定名称]

**内容**：约定的简要描述。

**原因**：在本项目中这样做原因。

**示例**：
\`\`\`typescript
// 如何遵循此约定
code example
\`\`\`

**相关**：相关约定或规范的链接。
```

### 添加新模式

```markdown
### 模式名称

**问题**：解决什么问题？

**方案**：方法的简要描述。

**示例**：
\`\`\`
// 好
code example

// 坏
code example
\`\`\`

**原因**：解释为什么这样更好。
```

### 添加禁止模式

```markdown
### 不要：模式名称

**问题**：
\`\`\`
// 不要这样做
bad code example
\`\`\`

**为什么不好**：问题解释。

**替代方案**：
\`\`\`
// 改这样做
good code example
\`\`\`
```

### 添加常见错误

```markdown
### 常见错误：描述

**症状**：出现的问题

**原因**：为什么会发生

**修复**：如何纠正

**预防**：将来如何避免
```

### 添加陷阱

```markdown
> **警告**：非明显行为的简要描述。
>
> 关于何时发生以及如何处理的具体说明。
```

## 交互模式

如果你不确定要更新什么，回答这些提示：

1. **你刚刚完成了什么？**
   - [ ] 修复了 bug
   - [ ] 实现了功能
   - [ ] 重构了代码
   - [ ] 讨论了方案

2. **你学到了或决定了什么？**
   - 设计决策（为什么选 X 而非 Y）
   - 项目约定（我们如何做 X）
   - 非明显行为（陷阱）
   - 更好的方法（模式）

3. **未来的 AI/开发者需要知道吗？**
   - 理解代码如何工作 → 是，更新规范
   - 维护或扩展功能 → 是，更新规范
   - 避免重复错误 → 是，更新规范
   - 纯粹的一次性实现细节 → 可能跳过

4. **它与哪个领域相关？**
   - [ ] 后端代码
   - [ ] 前端代码
   - [ ] 跨层数据流
   - [ ] 代码组织/复用
   - [ ] 质量/测试

## 质量检查清单

完成代码规范更新前：

- [ ] 内容是否具体且可操作？
- [ ] 是否包含代码示例？
- [ ] 是否解释了原因，而非仅内容？
- [ ] 是否包含可执行签名/契约？
- [ ] 是否包含验证和错误矩阵？
- [ ] 是否包含好/基准/坏案例？
- [ ] 是否包含所需测试及断言点？
- [ ] 是否在正确的代码规范文件中？
- [ ] 是否与现有内容重复？
- [ ] 新团队成员能看懂吗？

## 与其他命令的关系

```
开发流程：
  学到东西 → {{CMD_REF:update-spec}} → 知识被捕获
       ↑                                  ↓
  {{CMD_REF:break-loop}} ←──────────────────── 未来会话受益
  （深度 bug 分析）
```

- `{{CMD_REF:break-loop}}` - 深度分析 bug，通常揭示需要更新规范
- `{{CMD_REF:update-spec}}` - 实际执行更新
- `{{CMD_REF:finish-work}}` - 提醒检查规范是否需要更新

## 核心理念

> **代码规范是活的文档。每次调试会话，每次"顿悟时刻"都是让实现契约更清晰的机会。**

目标是**机构记忆**：
- 一个人学到的，所有人受益
- AI 在一个会话中学到的，延续到未来会话
- 错误变成文档化的护栏
