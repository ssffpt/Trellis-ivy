# Trellis 头脑风暴

## 不可妥协的访谈契约

就这个计划的每个方面对我进行不懈的追问，直到我们达成共同的理解。沿着设计树的每个分支逐一排查，逐个解决决策之间的依赖关系。对于每个问题，给出你的推荐答案。

每次只问一个问题。

## 不可妥协的证据规则

如果某个问题可以通过探索代码库来回答，那就直接去探索代码库。

这是强制性的。在向用户提问之前，先检查答案是否已经存在于代码、测试、配置、文档、现有规范或任务历史中。

不要请用户确认代码库能回答的事实。只询问关于产品意图、偏好、范围、风险承受能力或在检查后仍然不明确的事项。

---

在第一阶段规划期间使用此技能，将用户的请求转化为清晰的需求和规划产物。

## 前置条件

仅在已获得任务创建同意且用户准备好进入 Trellis 规划时使用此技能。

如果还没有任务，询问用户："需要我为你创建任务吗？"用户同意后执行：

```bash
TASK_DIR=$({{PYTHON_CMD}} ./.trellis/scripts/task.py create "<简短的任务标题>" --slug <slug>)
```

使用用户请求中的简洁标题。使用不带日期前缀的 slug。`task.py create` 会自动添加 `MM-DD-` 目录前缀。

`task.py create` 会创建默认的 `prd.md`。在提出后续问题之前，先用当前的理解更新该文件。

## 反模式："这个太简单了，不需要设计"

每个项目都要经过规划流程。一个配置变更、一个单函数工具、一个待办列表——全都需要。

"简单"的项目恰恰是未经检验的假设造成最多浪费的地方。设计可以很简短（几句话就够了），但你必须先展示出来并获得用户批准。

## UI 改动处理策略

- **简单 UI 改动**（如调整文案、修改颜色、单个元素状态变更）：使用下方"UI 描述格式"中的结构化描述（表格+状态机），无需原型。
- **需要视觉对齐的 UI 改动**：先用 ASCII 线框图快速呈现布局方向。用户不满意时，再提供 HTML 原型作为升级选项。

ASCII 线框图直接在对话中输出，无需创建文件。HTML 原型保存路径：`$TASK_DIR/prototype.html`（与 `prd.md` 同目录），使用纯 HTML + Tailwind CDN，独立于项目技术栈，仅作一次性视觉参考。

---

<HARD-GATE>
在你展示设计方案并获得用户明确批准之前，不要调用任何实现技能、编写任何代码、创建任何文件或采取任何实现行动。
这适用于所有项目，无论看起来多简单。
</HARD-GATE>

## 规划流程

1. 在 `prd.md` 中记录用户的请求和初始已知事实。
2. 在提问之前先检查可用证据：
   - 代码、测试、夹具和配置
   - README 文件、文档、现有规范和领域说明
   - 如有，相关的 Trellis 任务、研究文件和会话历史
3. 将发现的内容分为：
   - 已确认的事实
   - 仍需要从用户处了解的产品意图
   - 仍需要用户决定的范围或风险决策
   - 可能超出范围的事项
4. **提出 2-3 种方案。** 在展示单一设计之前，先探索不同的实现路径。对每种方案说明：
   - 方案的核心思路
   - 优点和缺点
   - 你的推荐及理由
   以对话方式展示选项，先展示你推荐的方案并解释原因。
5. 用户确认方案后，**涉及 UI 改动时，必须将已确认的视觉和交互决策（来自 ASCII 线框图或 HTML 原型）以结构化格式写回 `prd.md`。** 线框图和原型本身不作为实现依据，仅 `prd.md` 中的结构化描述才是 AI 编码时的参考。
6. 提出剩余问题中最有价值的一个。
7. 在问题中包含你的推荐答案。
8. 每次用户回答后，更新 `prd.md`，然后继续。
9. **PRD 门禁审核**：当 `prd.md` 中无 TODO/占位符、且所有已知问题都已讨论完毕时，AI 主动提议"prd.md 看起来已完整，是否启动门禁审核？"。用户回复"好"、"ok"、"审核"、"可以"、"开始吧"或类似肯定表达时触发。

   1. 调用 `trellis-review` 子代理，传入任务目录路径。**必须通过子代理执行，当前会话不得自行审核。**
   2. 审核子代理输出问题清单到 `$TASK_DIR/review.md`（**只审不改：禁止修改 `prd.md` 或目录下任何文件**）
   3. 若存在 C/H/M 级问题，由当前会话的规划 agent 修复 prd.md
   4. 修复后再次调度 `trellis-review` 重新审核
   5. **最多自动执行 3 轮**审核-修复循环。第 3 轮仍有 C/H/M 级问题时，暂停自动流程，向用户展示剩余问题，由用户决定：继续修复、缩小范围、或手动标记通过
   6. 用户选择"继续修复"时，每轮只执行一次修复-审核，然后暂停并展示结果，由用户确认后继续。如此循环，直到通过或用户选择其他选项

   用户只看最终审核结果，无需参与中间过程。

10. **请求实现批准**：门禁通过后，AI 向用户展示审核结论（`review.md` ✅）并提议"规划已完成，是否开始实现？"。用户回复"ok"、"好"、"开始"、"可以"或类似肯定表达后进入实现阶段。

不要编造项目特定的产品/规范层级。如果仓库中已有产品、领域或规范文档，请使用它们。如果没有，则基于现有证据继续。

## 提问规则

每次消息只问一个问题。

每个问题必须包含：

- 需要做出的决定
- 为什么这个答案很重要
- 你的推荐答案
- 如果用户选择不同方案的权衡

不要问流程性问题，例如是否搜索、检查文件或继续头脑风暴。直接完成证据工作。仅在剩余问题是关于产品决策、偏好、范围边界或风险承受能力选择时才询问用户。

## 产物规则

### 文件结构

所有任务只需 `prd.md`：

```
prd.md      — 需求、验收标准（"做什么"）
```

### prd.md 结构

记录需求、验收标准：

```markdown
# <Task Title>

## 目标

<why + what>

## 需求

* ...

## 验收标准

* [ ] ...

## 测试要求

> 具体测试类型参考项目 `.trellis/spec/` 中的测试策略。

* [ ] ...

## 超出范围

* ...

## 研究参考

* <links to research/*.md or external references>
```

### review.md 结构

记录门禁审核结果和修复历史：

```markdown
# <Task Title> - 审核记录

## 审核维度

| 维度 | 状态 | 备注 |
|------|------|------|
| 需求完整性 | ✅/⚠️/❌ | |
| 技术可行性 | ✅/⚠️/❌ | |
| 范围合理性 | ✅/⚠️/❌ | |
| 验收标准可测性 | ✅/⚠️/❌ | |

## 修复记录

- <每轮修复的内容>

## 最终结论

- <通过/不通过>

## 遗留问题

- <如有>
```

## UI 描述格式

涉及界面改动时，用以下结构描述，不要只用自然语言：

| 区域 | 内容 | 宽度 | 对齐 |
|---|---|---|---|

### 交互状态
| 状态 | 触发条件 | 效果 |
|---|---|---|

### 间距规范
- 卡片间距：16px
- 内边距：24px
- 圆角：8px

## 质量门槛

在宣布规划完成之前：

- `prd.md` 包含可测试的验收标准。
- 代码库可回答的问题已通过检查得到答案。
- 剩余的开放问题确实是关于用户意图或范围的。
- **PRD 已通过 `trellis-review` 门禁审核（`review.md` 最终状态为 ✅）。**
- **已提出 2-3 种方案并让用户做出选择。**
- **用户已明确批准规划产物。**
- **涉及 UI 改动时，视觉方向已确认（ASCII 线框图或 HTML 原型）且关键视觉/交互参数已同步到 `prd.md`。**

在用户明确批准之前，不要开始实现。如果用户说"开始吧"、"就这么做"、"ok"或类似的话，视为明确批准。不要用"默认继续"来替代明确批准。

## 规格自检

在最终提交规划产物之前，以全新的视角审视它们：

1. **占位符扫描：** 有没有"待定"、TODO、未完成的章节或模糊的需求？修复它们。
2. **内部一致性：** 各章节之间有矛盾吗？各需求之间是否一致？
3. **范围检查：** 这是否聚焦到可以用一个实现计划覆盖，还是需要进一步拆分？
4. **模糊性检查：** 有没有需求可以被两种方式理解？如果有，选择一种并明确写出来。

发现问题就直接内联修复。修好继续推进。
